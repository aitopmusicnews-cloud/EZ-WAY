# EZ-WAY AWS App Data

This stack replaces the former Supabase application backend with an AWS-native data layer. It is intentionally separate from `aws/audio-tools/`, which continues to own Music Intelligence jobs and DynamoDB analysis profiles.

## Architecture

- Amazon Aurora PostgreSQL Serverless v2 for relational EZ-WAY data.
- RDS Data API for Lambda SQL access without browser database credentials.
- API Gateway HTTP API + Node.js 22 Lambda for all application data access.
- Amazon Cognito User Pool JWT authorization for owner/admin routes.
- Private encrypted Amazon S3 bucket for audio, artwork, video, message images, and profile images.
- Public Share Portal routes are token-scoped and do not expose general table access.

## Fresh-start behavior

The schema starts empty. No old Supabase rows, storage objects, or browser cache are imported automatically. New data created after cutover becomes authoritative AWS data. Browser cache remains fallback/cache only.

## Files

- `template.yaml` — Aurora, Cognito, S3, Lambda, HTTP API, IAM, and outputs.
- `migrations/001_init.sql` — empty PostgreSQL schema.
- `scripts/migrate.mjs` — executes each migration statement separately through RDS Data API.
- `api/` — Lambda API, validation contract, storage signing, database helpers, and serializers.
- `deploy.sh` — deploys the stack, runs migrations, optionally creates the initial Cognito admin, and prints frontend values.
- `smoke-test.sh` — authenticated live CRUD/private-media/public-share verification with cleanup.

## Deploy from AWS CloudShell

Run this from a checkout of `feature/aws-music-intelligence` before changing any production frontend variables:

```bash
cd EZ-WAY
export AWS_REGION=us-west-2
export STACK_NAME=ezway-app-data
# Optional: creates the owner only when it does not already exist.
export ADMIN_EMAIL='you@example.com'
bash aws/app-data/deploy.sh
```

`deploy.sh` discovers the default VPC and its subnets, builds/deploys the SAM stack, applies the PostgreSQL migration, checks `/health`, and prints:

```text
VITE_EZWAY_API_URL=<verified API base>
VITE_COGNITO_USER_POOL_ID=<pool id>
VITE_COGNITO_USER_POOL_CLIENT_ID=<client id>
```

Do not apply those values to Amplify yet.

## Live smoke test

First complete the Cognito temporary-password challenge in the EZ-WAY sign-in UI if the admin was newly created. Then use the permanent owner password only as an ephemeral CloudShell environment variable:

```bash
export EZWAY_API_BASE='<EzwayApiBase>'
export COGNITO_USER_POOL_ID='<UserPoolId>'
export COGNITO_CLIENT_ID='<UserPoolClientId>'
export SMOKE_ADMIN_EMAIL='you@example.com'
read -s -p 'Owner password: ' SMOKE_ADMIN_PASSWORD; echo
export SMOKE_ADMIN_PASSWORD
bash aws/app-data/smoke-test.sh
unset SMOKE_ADMIN_PASSWORD
```

The smoke script never prints the password or ID token. It requires all of these to pass:

```text
health: ok
bootstrap: pass
private S3 upload/read: pass
track CRUD: pass
client/share creation: pass
public share resolve: pass
public play/feedback event: pass
cleanup: pass
LIVE APP-DATA SMOKE PASSED
```

Only after that live result should the three frontend values be copied into the Amplify environment while preserving every unrelated existing variable.

## Deployment safety

Do not expose the RDS master secret, AWS access keys, or any Cognito client secret to Vite/browser code. S3 application media stays private; temporary signed URLs are generated by the backend. The stack retains the S3 media bucket on stack deletion and snapshots Aurora on replacement/deletion to reduce accidental data loss.

The app-data smoke test does **not** replace the separate Music Intelligence smoke gate. `VITE_AUDIO_TOOLS_URL` and PR merge remain blocked until a real audio file reaches `completed` analysis with a usable saved profile.
