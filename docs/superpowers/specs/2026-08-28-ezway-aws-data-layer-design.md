# EZ-WAY Fresh AWS Data Layer Design

Date: 2026-08-28
Status: Approved direction; implementation pending review
Branch: `feature/aws-music-intelligence`

## 1. Goal

Replace the removed Supabase backend with a fresh AWS-native data layer while preserving EZ-WAY's existing UI, domain types, and `MediaStoreContext` behavior.

This is a fresh start. No Supabase rows or storage objects will be migrated. New EZ-WAY data will be created directly in AWS.

## 2. Principles

- Preserve existing `Track`, `Playlist`, `Client`, `Activity`, `ShareLink`, `UserProfile`, `Message`, and `PromoVideo` shapes unless an AWS transport concern requires an additive field.
- Keep `MediaStoreContext` as the app-facing state and mutation boundary so screens do not need a backend-specific rewrite.
- Remove `@supabase/supabase-js`, `src/lib/supabase.ts`, Supabase environment variables, Supabase schema auto-patching, and all Supabase-specific RPC/storage calls.
- Keep localStorage/localforage as an offline/cache fallback, not as the source of truth once AWS is reachable.
- Do not expose database passwords, AWS access keys, or administrative credentials in Vite/browser code.
- Keep Music Intelligence on its existing DynamoDB/SQS/Fargate path. Do not merge acoustic-analysis data into the main relational database.
- Keep media objects private in S3 and use time-limited presigned URLs for browser upload/download.

## 3. Recommended Architecture

```text
EZ-WAY React app (Amplify)
        |
        | HTTPS JSON
        v
API Gateway HTTP API
        |
        v
Lambda: EZ-WAY Data API
        |
        +---------------------> S3 private media bucket
        |                       - audio
        |                       - artwork
        |                       - video
        |
        v
RDS Data API
        |
        v
Aurora PostgreSQL Serverless v2
        |
        +-- tracks
        +-- playlists
        +-- clients
        +-- share_links
        +-- activities
        +-- messages
        +-- promo_videos
        +-- promo_packs
        +-- profiles
        +-- todos

Separate existing system:
EZ-WAY -> Audio Tools API -> SQS -> Fargate -> DynamoDB track-analysis
```

Aurora PostgreSQL is selected because the existing EZ-WAY schema is relational/PostgreSQL-oriented and can be carried forward with minimal semantic change. RDS Data API allows Lambda to execute SQL through an HTTPS service interface without maintaining long-lived database connections.

## 4. Authentication and Access

The old browser-side Supabase service-role pattern must not be reproduced.

Administrative data routes will require an authenticated EZ-WAY owner session. The implementation should use an Amazon Cognito User Pool authorizer for API Gateway, with one initial admin account. This adds a minimal sign-in gate without changing the internal catalog screens.

Public share-link access is the exception. It will use a narrowly scoped unauthenticated endpoint that accepts only a share token and can only resolve permitted share content and record access. Public callers will not receive general table access or mutation capabilities.

CORS will allow the production EZ-WAY origin and the Amplify origin, but CORS is treated only as browser policy, not authentication.

## 5. PostgreSQL Schema

The new database starts empty. The existing PostgreSQL schema remains the conceptual source, with migration cleanup where needed.

### Core tables

- `tracks`
- `playlists`
- `clients`
- `share_links`
- `activities`
- `messages`
- `promo_videos`
- `promo_packs`
- `profiles`
- `todos`

Primary keys remain UUIDs generated by the application or PostgreSQL. Existing UUIDs created by the frontend remain valid.

### Track storage fields

`tracks.file_url` and `tracks.image_url` remain compatible fields at the application boundary, but the database should additionally retain stable S3 object keys where needed. Persisting object keys avoids treating expiring presigned URLs as permanent identifiers.

Suggested additive fields:

- `file_key TEXT NULL`
- `image_key TEXT NULL`

API responses may resolve these keys to short-lived URLs before returning track objects to the frontend.

### Video storage

Likewise, `promo_videos` should store stable S3 object keys for persisted cloud videos rather than permanent public URLs.

## 6. Data API Contract

Create a backend-neutral frontend module such as `src/services/dataStore.ts`. `MediaStoreContext` will call this module instead of a Supabase client.

The module will expose operations aligned with the context's existing methods rather than exposing raw SQL/table syntax.

### Bootstrap

`GET /bootstrap`

Returns the owner workspace in one response:

```json
{
  "tracks": [],
  "playlists": [],
  "clients": [],
  "activities": [],
  "share_links": [],
  "messages": [],
  "promo_videos": [],
  "profile": null
}
```

This replaces the current startup sequence of separate Supabase table reads and makes the migration boundary simpler.

### Tracks

- `POST /tracks`
- `PATCH /tracks/{id}`
- `DELETE /tracks/{id}`

### Playlists

- `POST /playlists`
- `PATCH /playlists/{id}`
- `DELETE /playlists/{id}`

Track membership may remain represented by ordered UUID arrays initially for parity with the existing app. A normalized join table can be introduced later only if needed.

### Clients

- `POST /clients`
- `PATCH /clients/{id}`
- `DELETE /clients/{id}`

### Share links

- `POST /share-links`
- `DELETE /share-links/{id}`
- `POST /share-links/{id}/access`
- `GET /public/share/{token}`

### Activity and messages

- `POST /activities`
- `POST /messages`

### Profile

- `PUT /profile`

### Promo videos

- `POST /promo-videos`
- `DELETE /promo-videos/{id}`

## 7. S3 Media Contract

Create one private encrypted media bucket for EZ-WAY application media, separate from the Audio Tools output bucket.

Suggested key namespaces:

```text
tracks/audio/{trackId}/{uuid}-{filename}
tracks/artwork/{trackId}/{uuid}-{filename}
promo/videos/{videoId}/{uuid}-{filename}
messages/images/{messageId}/{uuid}-{filename}
profiles/{profileId}/{uuid}-{filename}
```

Upload flow:

1. Browser requests `POST /uploads/presign` with intended category, MIME type, filename, and related record ID.
2. Lambda validates the category, MIME type, object-size policy, and object key.
3. Lambda returns a short-lived S3 PUT presigned URL plus the stable object key.
4. Browser uploads directly to S3 using the presigned URL.
5. Browser stores the returned object key through the appropriate entity API operation.
6. Read responses resolve private object keys to short-lived GET URLs when required.

No AWS credentials are sent to the browser.

## 8. MediaStoreContext Migration

Keep the existing public context interface so components continue calling methods such as:

- `addTrack`
- `updateTrack`
- `deleteTrack`
- `addPlaylist`
- `addClient`
- `addShareLink`
- `sendMessage`
- `uploadFile`
- `updateProfile`

Internal changes:

1. Replace `getSupabaseClient()` initialization with a `dataStore.health()`/`dataStore.bootstrap()` sequence.
2. Replace `.from(...).select/insert/update/delete` calls with domain-specific `dataStore` methods.
3. Replace Supabase Storage upload with the S3 presign/upload flow.
4. Remove Supabase RPC schema-patch logic entirely. Schema changes are infrastructure migrations, never browser actions.
5. Preserve localStorage writes after successful state updates for offline/cache behavior.
6. On temporary AWS API failure, retain locally cached state and mark `connected=false`; do not erase local user data.

## 9. Infrastructure as Code

Add an isolated AWS application-data stack under a new directory such as:

```text
aws/app-data/
  template.yaml
  api/
  migrations/
  deploy.sh
  README.md
```

The stack will create/manage:

- Aurora PostgreSQL Serverless v2 cluster
- Secrets Manager database credential
- Data API enabled on the Aurora cluster
- private encrypted S3 media bucket
- Lambda data API
- API Gateway HTTP API
- Cognito User Pool / API authorizer
- IAM roles/policies with least-privilege access
- CloudWatch logs

The app-data stack must be independently deployable from `aws/audio-tools/` so database changes do not unnecessarily rebuild the Music Intelligence worker.

## 10. Configuration

Frontend production configuration becomes backend-neutral:

```env
VITE_EZWAY_API_URL=https://<app-data-api>
VITE_AUDIO_TOOLS_URL=https://3g3dmvsg67.execute-api.us-west-2.amazonaws.com
VITE_ALBUM_COVER_API_URL=https://albumcover-api.theartistcut.com
```

Cognito public identifiers required by the frontend may also be supplied as Vite variables. No Cognito secret, AWS secret, RDS credential, or IAM key may be exposed as a Vite variable.

Supabase variables are removed.

## 11. Fresh-Start Behavior

There is no Supabase import stage.

Initial `/bootstrap` response after deployment should contain empty collections and no user-created records. The application may retain local cached records already present in the browser, but it must not silently upload those records to AWS. New data entered after the AWS connection is enabled becomes the new authoritative cloud data.

If the user later wants to move selected local cached records into AWS, that will be a separate explicit import action.

## 12. Error Handling

- API responses use a consistent JSON envelope and HTTP status codes.
- Validation failures return `400` with a safe user-facing message.
- Missing records return `404`.
- Authentication failures return `401/403`.
- Database/storage failures return `5xx` without leaking SQL, credentials, bucket internals, or stack traces.
- The frontend retains the current local state when a remote mutation fails and displays/records an actionable error.
- Upload failures do not create a completed track record that points to a missing S3 object.
- Entity deletes should remove database references first and clean S3 objects in a controlled best-effort path; cleanup failure should be logged rather than corrupt relational state.

## 13. Testing Strategy

### Unit/contract tests

- API request validation and response serialization
- PostgreSQL row-to-domain mapping
- S3 object-key validation
- presign authorization/category checks
- public share-token access restrictions
- frontend `dataStore` contract
- MediaStoreContext migration behavior

### Infrastructure/static tests

- SAM/CloudFormation template validation
- no Supabase production imports
- no embedded database/AWS administrative credentials
- no browser-side direct RDS/DynamoDB/S3 SDK usage for privileged operations

### Live smoke tests

After deployment:

1. `/health` succeeds.
2. `/bootstrap` returns empty collections on the fresh database.
3. Create one track record.
4. Read it back through `/bootstrap`.
5. Upload one small media file through a presigned S3 URL.
6. Update the track with the returned S3 object key and verify playback/read URL resolution.
7. Create a client and share link.
8. Resolve the share through the public token endpoint.
9. Delete test data and confirm the database returns to the expected state.
10. Test EZ-WAY production UI end-to-end before enabling the new API URL as the production default.

## 14. Security Cleanup

As part of implementation:

- delete `src/lib/supabase.ts` after all callers are migrated
- remove `@supabase/supabase-js`
- remove Supabase env handling from Vite/server configuration
- remove obsolete Supabase schema-auto-patching code
- remove or archive Supabase-specific setup docs so they cannot be mistaken for current deployment instructions
- rotate/revoke the previously embedded Supabase service-role credential if its old project still exists
- add a CI check preventing `service_role` Supabase JWT patterns and direct Supabase imports from re-entering production code

## 15. Non-Goals

This migration does not:

- import old Supabase data
- merge the main app database with Music Intelligence DynamoDB
- redesign EZ-WAY screens
- change Albumcover Studio infrastructure
- normalize every legacy table immediately
- add advanced multi-tenant account/organization features
- merge PR #5 automatically

## 16. Completion Criteria

The migration is complete when:

- EZ-WAY starts with a fresh AWS PostgreSQL database and can create/read/update/delete new application data.
- Audio/artwork/video uploads use private S3 through presigned URLs.
- The browser contains no Supabase client, Supabase credential, RDS credential, or AWS administrative credential.
- Existing app screens operate through the unchanged `MediaStoreContext` interface.
- Local fallback remains available when AWS is temporarily unreachable.
- Music Intelligence continues to use its existing AWS Audio Tools + DynamoDB architecture.
- Production is not switched until live CRUD, upload, share-link, and Music Intelligence smoke tests pass.
